# Ask the Model v0.4.0

**Startup Qualification and Snapshot Integrity — 2026-09-22**

Ask the Model v0.4.0 retains the repository-grounded multi-chat capability introduced in v0.3.0 and adds a non-visual integrity layer for the installed application and local scientific-repository snapshots.

## Included

- asynchronous G-S0 startup qualification before local AI-provider discovery;
- effective Flatpak application/runtime identity inspection and deterministic platform fingerprinting;
- fail-closed qualification of the dedicated `~/Ask the Model` storage boundary;
- explicit unpackaged/development execution classification rather than treating a successfully started binary as a qualified release installation;
- durable startup-qualification records separated from volatile AI-provider availability;
- backward-compatible repository-state schema v2;
- deterministic local `snapshot seal v1` for validated repository snapshots;
- fail-closed seal comparison before a previously sealed snapshot can be reused;
- stable pre/post snapshot-integrity checks around retrieval-index validation or rebuild;
- legacy schema-v1 seal enrollment only after strict local snapshot/version/index validation succeeds;
- explicit same-SHA repair through the existing Download/Update action, with invalid snapshots quarantined for diagnosis before replacement;
- authoritative fail-closed G-S0 gating for non-empty repository grounding and repository mutation; read-only Refresh remains separate;
- independent G-O0 verification of persistent state, exact snapshots, snapshot seals, retrieval-index identity/integrity and source provenance;
- isolated lifecycle regression coverage that does not touch the user's real repository directory.

## Startup qualification

G-S0 runs offline. It does not perform repository Refresh or Download/Update.

For a packaged installation it qualifies the effective Flatpak application/runtime identity and the dedicated repository-storage boundary. EWD, CBD and RMD are then reconciled independently from persistent local state.

A clean installation with no local repositories remains valid: platform/storage qualification may pass while every repository is `NOT_INSTALLED`.

Malformed repository state remains fail-closed and is preserved for diagnosis rather than being replaced by heuristic snapshot selection.

The G-S0 installation result is also a runtime gate. A non-empty repository-grounded conversation and Download/Update remain unavailable until platform and storage qualification have passed. Ordinary zero-repository chat remains valid, and the explicit read-only Refresh action remains separate after qualification completes.

## Snapshot integrity

The exact upstream Git commit SHA remains the repository revision identity.

The new local snapshot seal is a separate deterministic SHA-256 integrity key. It is computed from sorted repository-relative paths, semantic regular/executable mode, file size and per-file SHA-256 content. Timestamps, UID and GID are excluded.

The seal therefore answers a narrower question: whether the local snapshot content still matches the content previously accepted by AtM. It does not replace the upstream Git SHA, Flatpak repository signatures or external release attestation.

Symlinks and unsupported filesystem entry types are rejected during seal computation.

## Repository lifecycle behavior

For download/update and conversation reuse, AtM now checks that snapshot content remains stable across index preparation:

`pre-seal → validate/reuse/rebuild index → post-seal → require equality`

A changed or mismatching sealed snapshot is not grounded into a conversation and is not silently repinned.

Legacy repository-state v1 remains accepted. Its seal is enrolled into schema v2 only after the existing strict snapshot/version/index reconciliation succeeds.

### Recovery after a local integrity failure

If an enrolled seal no longer matches, the repository is marked as requiring Download rather than remaining apparently current.

For an unchanged tracked SHA, AtM first downloads the exact-SHA archive. Only after that succeeds does it move the invalid real-directory snapshot to a diagnostic sibling quarantine name. The replacement then passes the normal bounded extraction, manifest/version validation, pre/post seal checks and index validation before SHA/version/seal state is persisted.

A symlink or non-directory snapshot path is not followed or silently replaced. If repair fails, AtM does not rewrite the persistent expected seal to match the damaged local content.

## Verification

The Flatpak/Meson CI gate covers:

- clean packaged-install startup qualification;
- explicit development/unpackaged classification;
- malformed persistent-state preservation;
- missing-snapshot classification;
- deterministic snapshot sealing independent of file creation order;
- content and executable-mode change detection;
- mtime stability;
- symlink rejection;
- schema-v1 to schema-v2 seal migration;
- wrong-SHA and malformed-seal rejection;
- G-S0 seal mismatch before index creation/rebuild;
- conversation-grounding rejection before index rebuild after local snapshot modification;
- activation of the existing Download action after integrity failure;
- preservation of invalid real-directory content through diagnostic quarantine and rejection of symlink quarantine;
- stable pre/post snapshot identity across index preparation;
- default fail-closed repository runtime before installation qualification;
- rejection of repository grounding and mutation after a negative startup qualification;
- independent G-O0 state/snapshot/index/source-provenance checks;
- repository-state v2 snapshot-seal recomputation by an implementation that does not link the production readiness/seal path;
- production READY followed by controlled post-validation perturbations, with rejection by the separately spawned oracle process;
- SQLite `integrity_check` and `foreign_key_check` divergence fixtures.

The existing repository-grounded retrieval and provenance tests continue to run unchanged. G-O0 is a test/diagnostic verification instrument, not a second runtime authority.

## User interface

v0.4.0 adds no new visual controls or layout changes. Startup qualification and snapshot-integrity verification are backend safeguards.

The existing AI-model selector, repository selector, Refresh, Download/Update, status LCD, multi-chat behavior and compact source references remain unchanged.

## Boundaries retained

v0.4.0 does **not**:

- install, start, stop or update the external AI provider;
- download/import/delete AI model files through AtM;
- persist conversations across application restarts;
- accept arbitrary unreviewed repository origins;
- execute or simulate EWD, CBD or RMD;
- autonomously modify scientific repositories;
- claim that a local snapshot seal is an upstream Git signature or release attestation;
- convert generated text into an authoritative scientific-model result.

EWD, CBD and RMD remain authoritative for their own model definitions, data, assumptions, provenance and validation.
