# Ask the Model v0.5.0

**Saved Conversation History and State Hardening — 2026-09-24**

Ask the Model v0.5.0 promotes the conversation-persistence, state-authority and publication-hardening work completed after v0.4.0. The main user-visible change is explicit saved conversation History: a chat is preserved only when the user activates **Save to History**, while ordinary Close continues to mean close without saving.

## Saved conversation History

- added an explicit **Save to History** control using the standard symbolic save icon;
- only conversations deliberately saved with that control persist as archived conversations;
- closing an unarchived chat, or exiting normally with an unarchived chat still open, discards that working conversation rather than silently adding it to History;
- the next startup removes unarchived leftovers from an interrupted prior process;
- History lists saved archived conversations only;
- History can reopen an archived conversation without silently unarchiving or repinning it;
- every History row provides **Open** and separately confirmed **Delete permanently** actions.

## Exact-context continuation

Saved conversations retain the model identity and repository context that produced them.

When an archived conversation is reopened, AtM reconstructs its durable transcript and citation provenance first, then requalifies the exact saved AI-model name/digest and repository generation/version/SHA context before continuation becomes available.

If the exact historical context is unavailable or mismatched, the conversation remains readable but view-only. AtM does not silently substitute a newer model or repository generation.

## Managed conversation exports

Archived conversations receive deterministic managed JSON mirrors under:

`~/Ask the Model/Conversation Exports/`

The export format preserves:

- conversation identity and timestamps;
- model name and optional digest;
- exact repository generation/version/SHA pins;
- provider and display message content;
- grounded state;
- citation provenance and immutable source permalinks.

Unarchived working chats do not create managed exports.

Permanent deletion is fail-closed across the archived SQLite conversation and its managed JSON mirror. AtM refuses to report permanent deletion successful while the managed export remains, and it will not follow a symlinked export root outside the qualified application storage boundary.

Import of these JSON archives is not implemented in v0.5.0.

## Hardened conversation persistence

The conversation store is separate from repository Control State.

Committed turns persist:

- exact frozen model/repository identity;
- provider-history and display content separately;
- complete user/assistant turn ordering;
- grounded citation provenance.

A provider-history update is allowed only after the corresponding durable SQLite turn succeeds. Persistence failure therefore cannot silently advance provider history beyond the last committed conversation boundary.

## SQLite Control State

Repository runtime authority on v0.5.0 uses the application-owned SQLite `control-state.sqlite3` path introduced after v0.4.0.

The promoted hardening includes:

- verified one-time legacy-state import/cutover;
- fail-closed precedence for an existing invalid Control DB;
- copy-on-write COMPLETE generations and atomic `active_state` advancement;
- expected-generation guards against stale writers;
- immutable historical generation reads for active/saved conversations;
- schema-v2 migration and trigger defense-in-depth;
- defensive/trusted-schema/DQS/trigger connection hardening;
- no-follow database opens;
- writable-authority verification;
- qualified XDG state-root ownership and permissions.

Legacy `repository-state.json` remains migration/recovery evidence rather than normal runtime authority.

## Startup qualification compatibility

The effective Flatpak runtime parser now accepts the real packaged runtime-ref form:

`runtime/ID/ARCH/BRANCH`

while retaining compatibility with the legacy `ID/ARCH/BRANCH` representation and still rejecting wrong ref kinds, IDs, architectures or branches.

The existing startup qualification, storage qualification and deterministic local snapshot-seal protections from v0.4.0 remain in force.

## Retrieval and provenance

The fixed EWD/CBD/RMD repository workflow remains unchanged in scientific scope:

- exact remote Git SHA/version Refresh;
- validated immutable local snapshots;
- deterministic per-snapshot retrieval indexes;
- first-Send model/repository freeze;
- current-turn-only repository grounding;
- compact numbered citations;
- exact repository/version/SHA/source/locator provenance;
- immutable source permalinks where available.

Production retrieval/context constants are now centralized so runtime and measurement tooling share one policy definition. A production-policy R5 companion records context-efficiency diagnostics, while the reviewed frozen R5 gate remains the blocking retrieval-quality qualification.

## Publication and development-channel hardening

The Flatpak workflow now separates read-only verification/build from main-only publication.

Publication receives only verified artifact outputs and the single scoped repository-content write permission required for release/development-repository publication.

Additional release safeguards include:

- draft-first GitHub Release creation before asset attachment;
- exact-commit release guards;
- fail-closed handling of immutable releases;
- explicit `SOURCE_COMMIT` traceability in the generated AtM Development repository;
- workspace-scoped Git trust rather than broad safe-directory exceptions.

## Verification

The v0.5.0 Flatpak/Meson and invariant gates cover the promoted state and conversation boundaries, including:

- Control DB bootstrap/migration/cutover and copy-on-write generations;
- stale-writer rejection and generation-consistent reads;
- state-root/no-follow/writable-authority qualification;
- durable conversation bootstrap and semantic validation;
- atomic ordinary and grounded turn commits;
- exact provider-history rebuild;
- immutable citation-permalink round-trip;
- exact historical repository/model continuation qualification;
- archive-only History and managed export creation;
- cleanup of unarchived working conversations;
- permanent-delete export failure handling;
- startup runtime-ref compatibility;
- existing repository snapshot-integrity, retrieval, grounding and provenance gates.

## Boundaries retained

v0.5.0 does **not**:

- install, start, stop or update the external AI provider;
- download/import/delete AI model files through AtM;
- expose arbitrary unreviewed repository origins beyond EWD/CBD/RMD;
- import conversation JSON archives;
- provide retention-policy or bulk History management;
- execute or simulate EWD, CBD or RMD;
- autonomously modify scientific repositories;
- turn generated prose into an authoritative scientific-model result.

EWD, CBD and RMD remain authoritative for their own model definitions, data, assumptions, provenance, validation and release boundaries.
